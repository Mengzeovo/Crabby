# 会话 / 对话 分层与缓存方案

Last updated: 2026-05-07

本文记录当前讨论中的方案目标：把“会话容器”和“可分叉对话分支”拆开，同时避免前端展示和 LLM 上下文组装在热路径上反复扫文件。

## 1. 核心结论

- `session` 是容器，不是具体的一段消息历史。
- `conversation` 是 session 下的一条消息分支，支持从某个节点继续对话。
- 给 LLM 的上下文只发“当前活跃分支的完整 lineage”，不发整个 session 的所有 conversation。
- 前端展示也只消费后端已经 materialize 好的活跃分支，不自己拼祖先链。
- 热路径缓存放在后端进程内存里，采用 TTL + LRU，落盘只负责事实数据和索引。
- 每个 `conversation` 都有自己的 `revision`；活跃分支缓存再额外计算一份 `branch_fingerprint`。
- `branch_fingerprint` 只用于判断活跃分支缓存是否过期，不作为 session / conversation / message 的业务 ID。

## 2. 推荐数据模型

### Session

Session 负责承载一个对话主题，以及当前默认落点。

```json
{
  "id": "s1",
  "title": "整理会话树方案",
  "created_at": 1715000000,
  "last_activity_at": 1715001234,
  "root_conversation_id": "c1",
  "active_conversation_id": "c3"
}
```

### Conversation

Conversation 负责承载一条可继续、可分叉的分支。

```json
{
  "id": "c3",
  "session_id": "s1",
  "parent_id": "c1",
  "fork_message_id": "m8",
  "revision": 4,
  "created_at": 1715000800,
  "last_activity_at": 1715001234,
  "title": "继续修正缓存方案",
  "message_count": 6,
  "file": "conversations/c3.json"
}
```

`fork_message_id` 很关键，它表示这个分支从父分支哪条消息之后切开。

## 3. 存储布局

推荐目录形态：

```text
sessions/
  s1/
    manifest.json
    conversations/
      c1.json
      c3.json
```

职责分工：

- `manifest.json`：索引层，只存会话树、顺序、活跃节点、统计信息。
- `conversation/*.json`：存完整消息正文。
- 不要把完整消息列表重复塞进 manifest。

## 4. 索引层做什么

索引层只负责“快速定位”，不负责“保存正文”。

它应该提供这些能力：

- 列出 session，按 `last_activity_at` 排序。
- 列出某个 session 下的 conversation 树。
- 定位当前活跃 conversation。
- 根据 `parent_id` 和 `fork_message_id` 还原 lineage。
- 给前端提供标题、消息数、更新时间、父子关系。

索引层不应该做的事：

- 不扫描整个目录树再临时排序。
- 不读取全部 conversation 正文来给列表页渲染。
- 不把自己变成另一份“大消息仓库”。

## 5. 热缓存怎么做

热缓存放在**后端进程内存**里，也就是 Python 服务运行时占用的 RAM。

推荐缓存一个“已经铺平的活跃分支”对象：

```python
branch_cache[(session_id, conversation_id)] = {
    "lineage": ["c1", "c2", "c3"],
    "branch_fingerprint": "sha256:c1:3|c2:4|c3:1",
    "messages": [...],
    "last_access_at": ...
}
```

工作方式：

1. 用户切到某个分支时，后端从索引层找到 lineage。
2. 后端按 lineage 读取对应 conversation 文件，拼成一条线性消息序列。
3. 这份序列放进内存缓存。
4. 用户继续发消息时，直接在缓存尾部追加。
5. 只有切分支、重启、祖先变更、压缩/迁移、缓存失效时才重建。

这份缓存不适合放 SQLite，因为它是热路径重复数据，最重要的是低延迟，而不是持久化。

### 5.1 保留窗口

- 缓存以 `(session_id, conversation_id)` 为粒度。
- 用户切走后，条目默认保留 **30 分钟** 无访问窗口；窗口内切回同一分支，应优先命中热缓存。
- 每次切回、追加消息、或再次读取上下文时，都刷新 `last_access_at`。
- 一旦发生祖先变更、分支压缩、显式失效、后端重启，缓存立即作废，不等 TTL。

### 5.2 容量预算

- 缓存大小用**序列化后的消息字节数**评估，不用 Python 对象数量估算。
- branch cache 没有独立的单条硬上限；热缓存只看全进程 **64 MiB** 预算。
- 全进程热缓存预算是 **64 MiB**，采用 LRU 逐出最久未访问的条目。
- 单条分支只要还能放进预算，就可以常驻热缓存；如果它太大导致总预算超限，也只会因为全局 LRU 规则被挤出。

这样切回原分支时，正常路径是内存命中；只有缓存失效时才回到磁盘重建。

### 5.3 指纹与版本

`revision` 是单个 conversation 的节点版本号，`branch_fingerprint` 是活跃分支缓存的总版本指纹。

推荐规则：

- 每个 `conversation` 都维护自己的 `revision`，默认从 `1` 开始。
- 会影响该 conversation 物化结果的变化时，`revision` 递增。
- `branch_fingerprint` 由当前 lineage 按顺序拼接 `conversation_id:revision` 后再 hash 生成。
- 计算结果要能区分节点版本，而不是只看内容全文。

示例：

```text
lineage = c1 -> c2 -> c5
branch_fingerprint = sha256("c1:3|c2:4|c5:1")
```

这里的 `3 / 4 / 1` 是各自节点的 `revision`，不是业务 ID，也不是全文 hash。它的作用是让后端快速判断“当前铺平后的分支历史”是否还和索引/落盘版本一致。

它不表示“这个 conversation 是谁”，身份仍然由 `session_id`、`conversation_id`、`message_id` 这些稳定 ID 表示。

推荐语义：

- ID 负责身份：`session_id` / `conversation_id` / `message_id`。
- `branch_fingerprint` 负责版本：当前 materialized 分支是不是仍然对应最新的 lineage。
- 当 `branch_fingerprint` 未变化时，同一分支继续发消息可以直接复用内存缓存。
- 当切换分支、祖先 conversation 变更、压缩/迁移、后台补写或缓存过期时，`branch_fingerprint` 会变化，后端应丢弃旧缓存并重建。

### 5.4 失效策略

MVP 先只做整条分支缓存失效：

- `branch_fingerprint` 不一致时，整条活跃分支缓存作废。
- 后端从 lineage 重新 materialize 一次。
- 这样实现简单，适合第一版。

后续如果性能需要，再做局部重建：

- 找到第一个 `revision` 不一致的 conversation。
- 保留它之前的缓存片段。
- 从该节点开始重新读取并拼接后续 conversation。

## 6. 给 LLM 的上下文规则

LLM 只看当前活跃分支的完整历史，顺序是：

`root -> ... -> fork ancestor -> active conversation`

不包含：

- sibling 分支
- 已经分叉出去的其他后续对话
- session 下无关的 conversation

实际拼接顺序建议由统一的 context builder 负责，而不是 REST、WebSocket、前端各拼一次。

## 7. 前端展示规则

前端展示应直接使用后端返回的“已 materialize 分支”：

- 会话列表按 `last_activity_at` 排序。
- session 内 conversation 树按稳定规则排序。
- 切换分支时只触发一次重建。
- 同一分支连续发言时，不重复做祖先链回溯。

这样前端看到的历史，和发给 LLM 的历史才会一致。

## 8. 迁移策略

旧的 flat JSON 首次加载时可自动迁成：

- 一个 session 目录
- 一个 root conversation
- 一个 manifest 索引

迁移后，老的单文件记录仍然可以被理解成“只有 root conversation 的 session”。

## 9. 推荐落地顺序

1. 先做 manifest / 索引层。
2. 再做后端内存 branch cache，以及对应的 TTL / LRU / 容量测试。
3. 再把 REST / WS / context-stats 接到统一的 context builder。
4. 最后改前端和桌宠的 session / conversation 展示。

这个顺序能保证先把“找得到、排得对、上下文不漏”跑通，再考虑更复杂的树状 UI。

## 10. 测试与验收

建议至少覆盖下面几类测试：

- 热命中测试：同一分支在 30 分钟内切回，应复用同一个 fingerprint，不重新扫 sibling 分支。
- 冷重建测试：超过 TTL 后切回，应从 manifest + lineage 重新 materialize。
- 容量测试：用小、中、大三类 fixture 叠加到超过 64 MiB 时，最久未访问条目先被逐出。
- 容量测试：测试一个1m上下文需要占用多少缓存，确保我们的会话缓存上限合适
- 口径测试：缓存大小必须按序列化字节数统计，不能只看 Python 对象个数。
- 退化测试：单条超大分支只要仍在 64 MiB 总预算内，就应能保留在热缓存；如果单条分支超过总预算，则应被全局 LRU 逐出。

如果后续要加性能回归，建议记录 warm hit 和 cold rebuild 的中位数 / p95，但先不要把墙钟时间写成过脆的 CI 门槛。
