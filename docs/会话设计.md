# Session / Conversation 分支设计

最后更新：2026-05-12

本文解释 Crabby 的会话模型。它面向维护者和前端实现者，用来保证后端、Obsidian 插件和 Desktop Pet 对“历史”“分支”“当前上下文”的理解一致。

## 核心定义

- **Session**：主题容器。它代表一个用户要持续推进的话题或任务。
- **Conversation**：session 下的一条可继续分支。它保存一段消息正文，并可从父 conversation 的某条消息 fork 出来。
- **Active branch**：从 root conversation 到当前 active conversation 的 lineage，按顺序铺平后的消息序列。
- **LLM context**：只包含 active branch，不包含 sibling branches。

这个设计解决两个问题：

1. 用户可以从任意消息 fork 新方向，而不污染主线。
2. 后端不需要每次请求都扫描整个 session 树来拼上下文。

## 数据布局

Session 数据存储在 `DATA_DIR/sessions/` 下：

```text
sessions/
  <session_id>/
    manifest.json
    conversations/
      <conversation_id>.json
```

旧版 flat session 文件 `sessions/<session_id>.json` 会在加载时迁移到新布局。

## Manifest

`manifest.json` 是索引层，不保存完整消息正文。它负责：

- session 元数据。
- root conversation。
- active conversation。
- conversation 树结构。
- 每个 conversation 的父节点、fork 点、revision、标题、消息数和更新时间。

示例：

```json
{
  "id": "s1",
  "title": "整理发布文档",
  "created_at": 1778515200,
  "last_activity_at": 1778518800,
  "root_conversation_id": "c1",
  "active_conversation_id": "c3",
  "conversations": {
    "c1": {
      "id": "c1",
      "parent_id": null,
      "fork_message_id": null,
      "revision": 7,
      "message_count": 14
    },
    "c3": {
      "id": "c3",
      "parent_id": "c1",
      "fork_message_id": "m8",
      "revision": 2,
      "message_count": 4
    }
  }
}
```

Manifest 不应变成第二份大消息仓库。列表页、树 UI 和 branch materialization 应依赖 manifest 找结构，再按需读取 conversation 正文。

## Conversation 文件

每个 conversation 文件保存该分支自己的消息正文和元数据。它只保存自己节点上的消息，不重复保存所有祖先消息。

`fork_message_id` 的语义是：当前 conversation 从父 conversation 的哪条消息之后分叉。Materialize active branch 时，父 conversation 只取到这个 fork 点。

## Active Branch Materialization

Materialization 的目标是生成一条线性消息序列：

```text
root -> ... -> fork ancestor -> active conversation
```

规则：

- 包含 active lineage 上的消息。
- 排除 sibling branch。
- 父 conversation 按子节点的 `fork_message_id` 截断。
- active conversation 包含自己的完整消息。
- REST、WebSocket、context-stats 和客户端历史展示应使用同一套 materialization 逻辑。

这样前端看到的当前分支历史和发给 LLM 的历史保持一致。

## Branch Cache

Active branch cache 是后端进程内存缓存，不是持久化事实源。

缓存 key：

```text
(session_id, conversation_id)
```

缓存内容：

```python
{
    "lineage": ["c1", "c3"],
    "branch_fingerprint": "sha256...",
    "messages": [...],
    "size_bytes": 12345,
    "last_access_at": 1778518800
}
```

当前策略：

- 30 分钟 inactivity TTL。
- 64 MiB 全进程预算。
- LRU 驱逐。
- 大小按序列化消息字节数统计。
- 不设单条 branch 独立硬上限；总预算控制所有缓存。

缓存命中场景：

- 用户在同一分支连续聊天。
- 用户切走后 30 分钟内切回同一分支。
- branch fingerprint 仍然匹配 manifest revisions。

缓存失效场景：

- TTL 过期。
- LRU 因全局预算驱逐。
- conversation revision 变化。
- lineage 变化。
- 后端重启。
- 显式迁移、压缩或缓存清理。

## Revision 和 Fingerprint

每个 conversation 有自己的 `revision`。任何会影响该 conversation materialized 结果的变化都应递增 revision。

Branch fingerprint 由 active lineage 的 `conversation_id:revision` 串计算：

```text
lineage = c1 -> c2 -> c5
fingerprint_input = "c1:3|c2:4|c5:1"
branch_fingerprint = sha256(fingerprint_input)
```

语义：

- ID 负责身份：`session_id`、`conversation_id`、`message_id`。
- revision 负责单个 conversation 的版本。
- branch fingerprint 负责判断缓存是否仍对应当前 active branch。

Fingerprint 不是业务 ID，不应暴露为用户可操作标识。

## Client Contract

客户端必须显式携带：

- `session_id`
- `conversation_id`

主要路径：

- `POST /sessions` 创建新 session 和 root conversation。
- `GET /sessions` 列 session。
- `GET /sessions/{session_id}/conversations` 取当前 session 树。
- `GET /sessions/{session_id}/conversations/{conversation_id}/messages` 取已 materialized 的分支消息。
- `WS /sessions/{session_id}/conversations/{conversation_id}/ws` 发送流式聊天。
- `GET /sessions/{session_id}/conversations/{conversation_id}/context-stats` 取该分支 context stats。

客户端不应该自己拼祖先链。后端返回的 materialized branch 是 UI 和 LLM 的共同口径。

## Fork Flow

典型 fork 流程：

1. 用户在某条消息上点击 fork。
2. 客户端请求后端基于该 `message_id` 创建新 conversation。
3. 后端在 manifest 中记录 `parent_id` 和 `fork_message_id`。
4. 新 conversation 成为 active conversation，或由客户端显式切换。
5. 后续聊天写入新 conversation。

Fork 后：

- 原分支保留不变。
- 新分支只继承 fork 点之前的祖先上下文。
- sibling branch 不进入当前 LLM context。

## Message IDs

后端负责生成和返回稳定 message IDs。

聊天完成时：

- REST response 携带 assistant `message_id` 和 `user_message_id`。
- WebSocket `done` event 携带 assistant `message_id` 和 `user_message_id`。
- Obsidian 插件用返回的 `user_message_id` 回填最新用户 bubble，使 fork action 立即可用。

客户端不应把临时 UI ID 当作持久 message ID。

## Context And Usage

Context stats 基于 active branch materialization。

字段口径：

- `context.total_tokens`：当前上下文窗口估算占用。
- `context.actual_usage.total_tokens`：provider 返回的当前回合 usage。
- `context.cumulative_usage.total_tokens`：session 持久化累计 usage。

Branch 切换后，context stats 应反映切换后的 active lineage。

## 安全校验

`session_id` 和 `conversation_id` 都必须：

- 只含 ASCII 字母、数字、`_`、`-`。
- 最长 128 个字符。
- 在任何磁盘读写前校验。

这条规则适用于 REST、WebSocket、context-stats、messages 和 session APIs。

## 测试重点

建议覆盖：

- unsafe session/conversation ID 在磁盘访问前被拒绝。
- legacy flat session 可迁移。
- active branch 排除 sibling 分支。
- fork_message_id 正确截断父 conversation。
- message ID 在 REST 和 WebSocket 完成事件中回传。
- branch cache warm hit。
- TTL 过期后 cold rebuild。
- LRU 在超过 64 MiB 预算时驱逐最久未访问项。
- serialized size accounting 不依赖 Python 对象数量。
- revision 变化导致 fingerprint 变化并失效缓存。

## 设计边界

当前实现没有自动摘要或 pruning。active branch 历史会完整保留，直到后续引入显式压缩策略。

未来引入摘要时，应遵守：

- 摘要是 conversation materialization 的一部分。
- revision 必须递增。
- branch fingerprint 必须变化。
- UI 需要能解释哪些历史被压缩。
