# Crabby 技术路线

最后更新：2026-05-12

本文说明 Crabby 的技术取向：当前系统为什么这样分层、下一步适合沿哪些边界增强，以及哪些方向暂时不应混在主干里。

这不是历史实施日志。发布后，本文应作为维护者判断技术路线的参考。

## 当前技术定位

Crabby 是一个本地优先、文件友好、Obsidian-centered 的个人 assistant 系统。它的主干不是“云端 SaaS”，也不是“只读知识库问答”，而是一个能在本地 Vault、LLM、工具、MCP 和桌面入口之间编排工作的运行时。

核心取向：

- **本地优先**：配置、session、附件、日志和 cron 数据默认在本机文件系统。
- **Obsidian 优先**：Obsidian 插件是最重要入口，`obsidian_search` 优先于裸文件 grep。
- **Provider 可切换**：LLM Profile 由后端拥有，插件做 UI 管理。
- **工具可控**：工具经统一注册、schema 校验、权限检查和结果格式化。
- **运行时可扩展**：Persona、Skill、Prompt、MCP 都是运行时配置，而不是硬编码单一路径。
- **发布可打包**：Obsidian 插件和后端二进制能组成一个手动安装 zip。

## 技术栈

| 层级 | 技术 | 作用 |
| --- | --- | --- |
| Backend | Python 3.11+, FastAPI, uvicorn | REST、WebSocket、admin、本地运行时 |
| Python package | uv | 依赖、测试、运行、PyInstaller 构建 |
| Models/config | Pydantic, pydantic-settings | API schema、工具 schema、环境配置 |
| LLM transport | httpx | Anthropic、OpenAI-compatible、Ollama |
| MCP | MCP Python SDK | 外部工具 server 连接 |
| Obsidian plugin | TypeScript, Obsidian API, esbuild | UI、设置、搜索桥、后端生命周期 |
| Desktop Pet | Electron, TypeScript, esbuild, Vitest | 桌面伴随入口 |
| Markdown render | marked, DOMPurify | Desktop Pet chat rendering |
| Cron | croniter | 定时任务解析 |
| Fetch | httpx, BeautifulSoup, markdownify | 网页/内容抓取 |
| Test | pytest, pytest-asyncio, Node scripts, Vitest | 后端、插件、桌宠验证 |

## 分层原则

### Backend 是能力中心

Backend 负责所有会影响模型行为或持久状态的事实源：

- LLM provider dispatch。
- LLM profile store/probe。
- Prompt assembly。
- Persona router。
- Skill loading。
- ToolRegistry。
- MCP runtime。
- SessionStore。
- AttachmentStore。
- Cron daemon。
- Context/token usage。

UI 客户端不应该复制这些业务判断。客户端只负责显示、输入、配置界面和本地宿主能力。

### Obsidian 插件是本地集成层

插件负责 Obsidian 内的事情：

- Chat view。
- Settings UI。
- Backend lifecycle。
- Runtime config seeding。
- Host heartbeat。
- Obsidian Search DSL。
- Client-hosted tools。
- Vault path synchronization。

插件可以镜像后端 profile 状态用于渲染，但 profile 的保存、删除、激活和测试必须走后端 admin APIs。

### Desktop Pet 是伴随入口

Desktop Pet 复用后端，不另起一套 AI 逻辑。它适合承担：

- 轻量聊天。
- 气泡提醒。
- 后台通知展示。
- Transcript 恢复。

复杂设置、MCP 编辑和 Vault 搜索仍以 Obsidian 插件为主。

## 关键架构方向

### 1. LLM Provider 层继续收敛

Provider preset 应保持保守：

- 只发送该 provider 明确支持的 request fields。
- usage normalization 放在后端统一处理。
- reasoning/thinking 输出统一进入 shared content shape。
- provider-native 特性先以显式能力接入，不要因为 OpenAI-compatible 就盲目透传所有字段。

短期重点：

- 保持 Anthropic、OpenAI、Ollama 和国内 OpenAI-compatible preset 稳定。
- 强化 `/admin/profile/test` 的错误提示。
- 为新 provider 增加测试覆盖：request allowlist、output adapter、usage parsing。

中期可做：

- 更细粒度的 model capability metadata。
- provider 原生文件、图像、web search、code interpreter 能力的显式封装。

### 2. Session / Conversation 是长期主干

当前 session/conversation split 是 Crabby 的长期基础：

- session 是主题容器。
- conversation 是可继续分支。
- active branch 是 LLM 历史单位。
- sibling branches 不进入当前上下文。
- branch cache 解决热路径 materialization 成本。

短期重点：

- 保持 REST、WebSocket、Obsidian plugin、Desktop Pet 的 `session_id + conversation_id` 合同一致。
- 增强 branch cache 的测试和观测。
- 为 fork、switch、message ID backfill 保持 UI/后端一致。

中期可做：

- 长会话摘要和 pruning。
- branch-level usage/metadata。
- 更清晰的 conversation tree UI。

### 3. 工具系统走“受控自动化”

工具是 Crabby 从聊天壳变成 assistant 的关键，但也是主要风险面。

技术方向：

- 所有工具都通过 Pydantic schema 校验。
- 所有写入工具都应有明确权限语义。
- UI 展示的 tool state 和注入 LLM 的 tool result 应保持分离。
- 大结果需要截断、摘要或落盘策略，避免撑爆上下文。
- `obsidian_search` 是 Vault 知识检索首选；裸文件工具是补充。

短期重点：

- 写文件、shell、settings、cron 的确认和审计体验。
- 工具错误的可读性和可恢复性。
- 受限 tool context 的测试覆盖。

中期可做：

- per-profile 或 per-session tool toggles。
- tool audit log。
- read-only / write / destructive 元数据。
- 工具前后 hook。

### 4. MCP 是外部扩展边界

MCP 适合外部系统，不适合塞进 Crabby 核心。

原则：

- MCP config 只描述 server，不硬编码 secret。
- `${ENV_VAR}` 插值是 secret 的推荐路径。
- reload 继续保持事务式。
- MCP status 必须可观测。
- MCP 工具注册失败不应破坏已有工具集。

短期重点：

- 插件设置页的 MCP 配置体验。
- 错误定位和重载结果展示。

中期可做：

- MCP 工具来源和权限分组。
- 单 server reload。
- MCP 工具审计。

### 5. Persona / Skill / Prompt 是行为配置层

Persona、Skill 和 Prompt 不应散落在代码里。

技术方向：

- Prompt fragments 优先从 `PROMPTS_DIR` 读取。
- Persona 从 `PERSONA.md` 发现。
- Skill 从 `SKILL.md` 发现。
- 插件首次运行 seed 默认模板，但不覆盖用户已修改文件。
- Auto persona router 只在需要时锁定 session persona。

短期重点：

- 保持默认 persona 模板和 repo persona 一致。
- 提升 Auto router 的可解释性。
- 让用户更容易理解当前 persona/skill 为什么生效。

中期可做：

- Persona/Skill UI 编辑。
- Prompt diff/reset。
- Skill allowed-tools 约束。

### 6. Cron 走轻量后台 agent

Cron 当前适合提醒、周期检查和低频自动化。

原则：

- Cron 执行用隔离 session。
- 不复用源 conversation context。
- 完成摘要写回源 session。
- 执行前等待 session idle。
- 和 REST/WS 共享 agent runner 迭代上限。

短期重点：

- 更好的 cron 列表/删除 UI。
- 失败通知和重试策略。
- cron job 输入的安全边界。

中期可做：

- 用户确认型后台任务。
- Morning briefing。
- 任务依赖和状态面板。

## 发布路线

当前发布方式是私有手动安装：

1. 在目标平台构建 backend binary。
2. 构建 Obsidian plugin `main.js`。
3. 用 `scripts/package-obsidian-release.py` 打包 zip。
4. 用户解压到 Vault 的 `.obsidian/plugins/`。

短期路线：

- 保持 `runtime/state.json` 相对路径机制稳定。
- 明确平台/架构包命名。
- 改善 macOS quarantine 和 executable bit 文档。
- 增加 Windows/Linux 打包验证。

中期路线：

- 自动构建 release matrix。
- 签名、校验和升级策略。
- 更完整的安装器或插件内更新流程。

## 不应过早做的事

这些方向有价值，但不应在主干不稳定时提前引入：

- 多用户云端账号系统。
- 把所有状态迁移到重型数据库。
- 内置向量数据库作为第一版长期记忆核心。
- 无确认的大规模自动改写 Vault。
- 把 provider 原生高级能力混在 generic OpenAI-compatible 层里。
- 为 Desktop Pet 复制一套独立配置和会话系统。

## 验证策略

按影响面选择最小足够验证：

- Backend API/tool/session/provider 改动：pytest。
- Python style/import 改动：ruff。
- Obsidian config/runtime/search/chat 改动：对应 Node test、`tsc --noEmit`、build。
- Desktop Pet 改动：typecheck、Vitest、build。
- 跨模块合同改动：后端和对应客户端一起跑。

常用命令：

```bash
cd server
uv run pytest
uv run ruff check .
```

```bash
cd obsidian-plugin
npm run test:config
npm run test:chat-content
npm run test:chat-styles
npx tsc --noEmit
npm run build
```

```bash
cd desktop-pet
npm run typecheck
npm run test
npm run build
```

## 下一阶段优先级

1. 完善发布包跨平台验证和安装文档。
2. 强化写入类工具的用户确认和审计。
3. 改善 session tree / fork / branch switch 的用户体验。
4. 建立更成熟的长会话摘要和上下文预算管理。
5. 扩展 Desktop Pet 的通知与轻量任务体验。
6. 为 MCP、profiles、provider output adapters 增加更系统的回归测试。
