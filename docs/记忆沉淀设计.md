# 记忆沉淀设计

最后更新：2026-05-21
状态：第一版核心已实现（memory_write / memory_search / registry / layout / auto-save 采集窗口），部分能力待实现。

## 文档定位

本文记录 Crabby 长期记忆沉淀机制的设计取向、边界划分和关键决策。它的上游是
[growth-vision.md](growth-vision.md) 中"维度一：用户反馈/成长"的 P0 能力；下游是
已落地的 `server/memory/` 模块（facets、layout、registry_store、name_index）、
`server/tools/memory_write.py`、`server/tools/memory_search.py`，以及已切换到
本地记忆工具的 auto-save 采集链；Diary skill 和 MemPalace 双写仍待实现。

本文不是实施计划，也不是 API 规范。它回答三个问题：

1. 记忆应该存在哪里？
2. 记忆应该按什么维度组织？
3. Diary、MEMORY.md 与"长期记忆"的关系是什么？

## 现状与问题

> **2026-05-21 更新**：`auto_save_daemon_loop` 已切到 `memory_search` /
> `memory_write`，并在入队时冻结 `session_id`、`conversation_id`、
> `branch_fingerprint` 和待审阅消息窗口。session manifest 现在保存
> `auto_save_checkpoints`，按 conversation 记录已审阅到哪个 `message_id`。
> MemPalace-only auto-save 已成为历史问题；MemPalace 双写仍待第五步实现。

改造前，`auto_save_daemon_loop` 把处理时的当前对话窗口喂给一个后台 LLM agent，
工具白名单仅限四个 `mempalace_*` 工具。一旦 MemPalace MCP 没连，auto-save
直接 return，没有任何保底落点。

这导致两个具体问题：

- **没有 MemPalace ≠ 记忆缺失，而是整条沉淀链断开**。session 文件本身只是对话回放，
  不是"记忆"。
- **MemPalace 不是 source of truth 的合适位置**：它是独立子进程、独立数据格式、独立
  生命周期；用户无法直接读、改、备份；Vault 才是用户已经在用的本地知识库。

更根本的问题是设计意图错位：Crabby 的本地优先承诺要求"用户数据永远在本地 Vault，
不需要账号"，但当前主干把核心记忆放在了一个外部 MCP 子系统里，违背了这个原则。

## 行业调研

调研了 Anthropic 和 OpenAI 在 2026 年的做法（详见调研对话和外链）。两家在以下点上
一致：

| 维度 | 共识做法 |
| --- | --- |
| 沉淀边界 | **项目 / 仓库 / workspace**，不是 session |
| Session 角色 | 临时上下文 + 写入触发器，不持有"记忆" |
| 组织维度 | 按"类型 / 主题"，不按时间 / 会话 |
| 入口形态 | 索引文件先加载（Claude 是 `MEMORY.md`，OpenAI 是 system instructions） |
| 共享语义 | 默认项目内共享，跨项目隔离 |

具体参考：

- **Anthropic Memory Tool**（API 原语）：模型操作 `/memories` 虚拟目录，客户端决定
  实际存储；系统 prompt 强制每个 session 开始前先 `view /memories`。
- **Claude Code auto-memory**（产品形态）：路径 `~/.claude/projects/<repo>/memory/`，
  按 git 仓库根硬隔离；入口 `MEMORY.md` 仅前 200 行进 system prompt；按 user / feedback
  / project / reference 四类组织；明确规定"能用 grep 或 git 拿到的不要写进 memory"。
- **ChatGPT Projects**：项目作为边界容器，支持 project-only 和 default 两种 memory
  模式，共享项目强制 project-only。

最重要的结论：**Session 不是合适的沉淀边界**——它太短命、太碎片。值得保留的语义
单元是项目 / 主题 / 类别。

## 设计决策

### 决策 1：Vault 是 source of truth，MemPalace 是派生索引

| 角色 | 放哪 | 理由 |
| --- | --- | --- |
| Canonical store（记忆原文） | **Vault Markdown** | 已在 Obsidian 里；Sync/git 备份；MemPalace 挂了数据还在；用户可手改 |
| 向量召回 | **MemPalace** | 它擅长这个，没必要重造 |
| 知识图谱 | **MemPalace** | 同上，纯派生数据 |

写入顺序：auto_save agent 先通过**专用记忆工具**把内容写到 Vault Markdown，**然后**
再调 `mempalace_*` 索引到向量库。MemPalace 不在线时仍有保底；MemPalace 重建索引时
只需重读 Vault。

后台记忆 agent **不允许使用通用 `edit` 工具**。第一版应提供受限的记忆工具，例如：

- `memory_write`：创建或更新单条 memory 文档，只能写 `<vault>/.crabby/memory/`。
- `memory_search`：按 facet 字段和 registry 查询记忆元数据。
- `memory_registry_update`：原子追加或规范化 topic/domain；也可以由 `memory_write`
  内部完成。

这样保底写入不依赖 MemPalace，也不会把整个 Vault 的写权限交给后台 agent。

### 决策 2：沉淀边界是"项目 / 主题 / 类型"，不是 session

session_id 仅作为溯源元数据写入 frontmatter，不进入目录结构。session 删除时，溯源
链可能断，但跨 session 的事实/决策保留。

这里要区分两件事：

- **采集来源**：一次具体 session/conversation 的近期上下文。
- **沉淀边界**：写入后的 `type` / `topic` / `domain` / `valid_from..valid_to` 等
  facet。

也就是说，记忆当然来自一次会话中的信息，但它不按会话组织。auto-save 触发时应记录
`session_id`、`conversation_id`、`branch_fingerprint` 和消息范围，后台处理时使用触发
时的 active branch snapshot 或等价的固定窗口，避免用户切换分支后沉淀到错误上下文。

### 决策 3：按"类型"分目录，参考 Claude Code 的四类

| 目录 | 内容 | 例子 |
| --- | --- | --- |
| `user/` | 关于用户本人的事实 | 角色、背景、偏好、知识基线 |
| `feedback/` | 用户对 assistant 的纠正与确认 | "不要总结"、"使用 pnpm 而非 npm" |
| `project/` | 当前主题/项目的事实和决策 | 架构选择、调研结论、规划 |
| `reference/` | 外部系统指针 | "issue 在 Linear ENG 项目"、"日志看 grafana xxx" |

每条记忆是一个独立 Markdown 文件。`project/` 内部按 topic 建二级目录；其他类型也
可以用 topic 目录承载局部约束，例如 `feedback/general/` 和
`feedback/crabby-记忆设计/`。topic 由 LLM 在写入时决定，但**写入前 agent 必须先读
registry，选择已有 topic 或显式创建新 topic**，避免新主题漂移。

domain 不进入目录结构。它是横向标签字段，一条记忆可以有多个 domain；如果把 domain
做成目录，会立刻遇到重复文件或软链接问题。横向查询由上层工具按 frontmatter 过滤
完成，目录只承担纵向归属。

后续可以做"记忆聚合"来减少碎片：定期把同 topic、同 kind 的多条小记忆合并为一条
summary memory，原记忆标记为 `state: archived`，新记忆用 `derived_from` 保留来源。
聚合是维护任务，不阻塞第一版写入路径。

### 决策 4：Facet 模型是记忆的核心检索字段集

每条记忆的 frontmatter 包含一组 facet 字段：`type` / `topic` / `domain` / `kind` /
`state` / `valid_from` / `valid_to`。这是写入时必须填好的核心检索字段，定义记忆
**如何被分类和过滤**——怎么使用这些信息（结构化召回、语义检索、聚合归档等）由
上层工具决定。

facet 模型不等于完整 frontmatter。`name`、时间戳、`related` / `supersedes` /
`derived_from`、`session_id` / `conversation_id` / `branch_fingerprint` 也会写在
frontmatter 里，但它们分别属于身份、维护、链接和溯源元数据，不纳入 facet 字段集。

facet 模型本身不规定召回方式。它只承诺：每条记忆都按统一检索字段落盘，frontmatter
形态稳定、可扫描、可重建索引。具体到第一版，会先有一个 `memory_search` 工具消费
facet 字段做结构化过滤；MemPalace 在线时，`mempalace_search` 在同一份记忆数据上
提供语义召回通道，与结构化过滤互补。

把"数据结构"与"召回方式"解耦后，未来扩展上层手段（聚合、KG 推理、新的搜索通道
等）都从同一份 frontmatter 出发，不需要改动写入路径。

### 决策 5：Diary 由内置 skill 管理，存放在用户配置的 Vault 路径

Diary 不归属 `<vault>/.crabby/memory/`。理由：

- Diary 是**用户的产物**，不是 assistant 的"内部记忆"。用户可能已经有自己的 Daily
  Notes 习惯和文件夹约定（例如 `Journal/2026/05/`）。
- Diary 应该**对用户高度可见**，鼓励直接打开、阅读、补充。把它埋进 `.crabby/`
  反而违背了"日记"的语义。
- Diary 写入需要**模板化**——固定的章节结构、固定的 frontmatter，让用户翻阅时有
  预期。模板由用户提供或由 Crabby 内置默认。

Diary 的行为规范放进一个内置 `diary` skill：它携带默认模板、追加规则、修改边界和
写作口径，指导 LLM 以稳定格式写入和维护日记。实际写入仍应通过受限的 diary 专用能力
或插件桥完成，不通过通用 `edit` 工具。

具体形态见下文"Diary 设计"。

### 决策 6：`MEMORY.md` 是读取规则和热入口，不是全量记忆索引

`<vault>/.crabby/memory/MEMORY.md` 保留，但定位从"全量目录"调整为"assistant 读取记忆
的规则与热入口"。它可以被注入 system prompt，帮助 assistant 知道如何使用
`memory_search` 和 registry，而不是试图列出所有记忆。

```markdown
# Memory Operating Rules

- 先用 `memory_search(mode="list_registry")` 查看已有 topic/domain。
- 当前 topic 下优先召回 `topic=<current>` 的 project/feedback/reference。
- 全局约束召回 `type=user|feedback, topic=general`。
- domain 用于跨 topic 横向召回；默认只读取 `state=active`。
- 局部 feedback 覆盖 general feedback。

# Hot Entries

- 当前维护重点：crabby-记忆设计
- 常用全局 topic：general
```

约束：

- 它不是 source of truth，也不是全量索引。
- 事实源是单条 memory Markdown 文件及其 frontmatter。
- 机器索引可以由 frontmatter 扫描重建；`MEMORY.md` 不应破坏性截断记忆可发现性。
- 加载策略：会话开始时注入 `MEMORY.md` 的规则和热入口；具体内容按需调用
  `memory_search` / `read` 加载。

## Facet 模型（多维度检索结构）

facet 模型是记忆 frontmatter 中用于分类、过滤和索引的核心字段集。它不覆盖完整
frontmatter：链接、溯源、时间戳等字段仍然保存在文件头里，但不属于 facet。facet
模型也不是召回机制，召回方式（结构化过滤、语义检索、聚合归档）由上层工具消费
这些字段实现。

引入多维度 facet 的动机是：仅靠 `type` 单维度无法支持"跨项目复用同类经验"。例如
Crabby 项目里关于 cron 失败重试的经验，半年后做另一个项目时按 topic 找不到——经验
是跨 project 的，但只挂在 topic 上等于把横向知识压扁成纵向。多维度 facet 让同一条
记忆同时承载"诞生在哪"（topic）和"讲哪类问题"（domain），上层工具据此组合出多种
查询路径。

### 核心维度（必填）

| 维度 | 答的问题 | 例值 |
| --- | --- | --- |
| **type** | 这是什么性质的记忆 | `user` / `feedback` / `project` / `reference` |
| **topic** | 它属于哪个项目/主题 | `crabby-记忆架构` / `健身计划` / `typescript-学习` |
| **domain** | 它涉及什么横向领域 / 技能 | `cron-scheduling` / `error-handling` / `vector-search` |

**topic vs domain**：

- **topic 是纵向边界**——回答"这条记忆诞生于哪"，答案是项目名、主题名、生活领域容器。
  一个项目结束后 topic 基本不再增长。
- **domain 是横向标签**——回答"这条记忆讲的是哪类问题"，答案是技能名、问题类别名、
  模式名。它跨项目存在，下次遇到同类问题应该把它捞回来。
- **广度召回靠 domain**——按 `topic=crabby-架构` 找不到的 cron 经验，按
  `domain=cron-scheduling` 能跨项目召回。

判断方法（写入时问两个问题）：

1. "这条记忆诞生于哪？" → topic
2. "这条记忆讲的是哪类问题？" → domain

只能想到 topic 没想到 domain：多半是项目特定细节，不必复用，留空 domain 即可。
只能想到 domain 没想到 topic：多半是关于用户本人的通用事实，type 应为 `user`，
topic 填 `general` 或留空。

边界 case 示例：

| 记忆 | type | topic | domain |
| --- | --- | --- | --- |
| Crabby 后端用 FastAPI | project | crabby-架构 | （可空） |
| Crabby cron 失败要指数退避 | project | crabby-架构 | cron-scheduling, error-handling |
| 我一般用 pnpm 不用 npm | feedback | general | tooling |
| TypeScript 的 `as const` 怎么用 | project | typescript-学习 | type-system |
| 我对死线压力反应大 | user | general | self-knowledge, stress-management |
| 银行核心系统采用事件溯源 | project | xxx-银行 | finance, architecture, event-sourcing |

### domain 是数组：交叉点知识的处理

一条记忆可以挂**多个 domain**。这是必要的——知识常常处于多个领域的交叉点，强行归到
单一 domain 会丢失一边的召回路径。例如银行核心系统的架构决策同时属于 `finance` 和
`architecture`，按任一查询都应能召回。

但多 domain 不能滥用。两个反模式：

1. **贴标签式滥用**：把所有沾边的 domain 都挂上。判断标准是"未来按这个 domain 查询，
   是否会希望这条出现在结果里"——否则不挂。
2. **颗粒度混搭**：同一条记忆既挂 `tech`（太宽）又挂 `python-asyncio-locking`（太窄）。
   domain 应处于中等抽象层级，跨项目能被自然想到，又不至于宽到"什么都是"。

经验法则：

- 2–4 个 domain 是合理上限，多于 5 个先考虑拆成多条记忆。
- 想象 6 个月后的查询，哪些关键词会被自然想到，只挂这些。
- 同义不并列（不要既挂 `cron` 又挂 `cron-scheduling`，选稳定那个）。
- 写入前先 list 已有 domain，让 LLM 选已有或新建，避免同义漂移。

### 辅助维度（选填）

| 维度 | 答的问题 | 例值 |
| --- | --- | --- |
| **kind** | 知识形态 | `fact` / `rule` / `pattern` / `mistake` / `goal` / `case` / `reflection` |
| **state** | 还有效吗 | `active` / `archived` / `invalidated` |
| **valid_from** | 事实何时开始为真 | `null`（一直为真）/ `2026-05-19` |
| **valid_to** | 事实何时失效 | `null`（仍然有效）/ `2026-06-30` |

`valid_from` + `valid_to` 拆成两个字段而非单字符串，理由：
- `memory_search` 可直接做日期比较过滤（"给我所有当前有效的记忆"），不需要解析格式。
- 与 MemPalace KG 的 `valid_from`/`valid_to` 语义一致，双写时零转换成本。
- `valid_from: null, valid_to: null` 等价于"永远有效"。

`kind` 是单值，回答"这条记忆的主要知识形态是什么"。第一版保持词表克制：

- `fact`：当前为真的事实、状态或已经落定的选择。过去的 `decision` 归入 `fact`，理由和取舍写在正文。
- `rule`：未来应遵守的约束、偏好或操作规范。
- `pattern`：可复用经验、套路、判断方法，不是强制规则。
- `mistake`：曾经出错、误判或踩坑，未来需要避免或复盘。
- `goal`：想达成的目标、计划或追踪对象。
- `case`：具体案例、经历、故障现场或学习样本。
- `reflection`：对经历、状态、选择或情绪的复盘理解，不一定能直接转成规则或模式。

如果一条记忆同时像多个 kind，优先选择它未来最可能被怎样召回；确实承担两种用途时拆成两条。

### 链接维度（选填）

- `supersedes: [name]` — 取代某条旧记忆（旧的应同步标 `state: invalidated`）。
- `related: [name, name]` — 相关引用，建轻量记忆图谱。
- `derived_from: [name, url]` — 来源溯源（与已有会话/message 溯源互补）。

### topic 对所有 type 生效（包括 feedback）

`topic` 不只是 `project` 类的属性——**所有 type 都应带 topic 来限定作用域**。

| type | topic | 含义 |
| --- | --- | --- |
| feedback | `general` | 全局约束，任何上下文都生效 |
| feedback | `crabby-架构` | 只在 Crabby 项目上下文里约束 |
| feedback | `typescript-学习` | 只在学 TS 时约束 |
| user | `general` | 用户的通用事实 |
| user | `健身计划` | 用户在健身这个领域的特定状态 |
| reference | `general` | 通用外部指针 |
| reference | `crabby-架构` | 只在 Crabby 项目里才需要查的外部源 |

这意味着 assistant 在某个 topic 上下文里工作时，应该：

1. 加载 `topic=general` 的 feedback/user（全局约束）。
2. 加载 `topic=<当前 topic>` 的 feedback/user（局部约束）。
3. 两者冲突时，**局部优先**（更具体的约束覆盖更泛的）。

### Registry：facet 词表索引

为避免同义漂移（`cron` vs `cron-scheduling` vs `scheduled-tasks`），系统维护一个
**Registry 文件**，列出当前所有已使用的 topic 和 domain 值。

路径：`<vault>/.crabby/memory/REGISTRY.md`

格式：

```markdown
# Memory Registry

## Topics

- general
- crabby-架构
- crabby-记忆设计
- 健身计划
- typescript-学习
- 个人成长

## Domains

- cron-scheduling
- error-handling
- architecture
- vector-search
- type-system
- tooling
- self-knowledge
- stress-management
- finance
- habit-tracking
```

**写入协议**：

1. agent 写入新记忆前，**必须先读 `REGISTRY.md`**。
2. 检查要用的 topic/domain 是否已存在。
3. 如果已有语义相同的词（例如想写 `cron` 但已有 `cron-scheduling`），**复用已有词**。
4. 如果确实是新领域，新建词条并**同步追加到 `REGISTRY.md`**。
5. `type` 是固定 4 值，不需要 registry。

这等价于一个轻量的"受控词表"——不是硬编码预定义，而是**随使用生长但有去重约束**。

Registry 更新必须由专用工具完成，不能让 LLM 直接编辑文件。工具需要保证：

- 原子写入，避免并发 auto-save 互相覆盖。
- 写前重读，发现重复或同义候选时返回给 agent 复用。
- 可校验，可从所有 memory frontmatter 反向重建或检查漂移。
- 第一版不做复杂 aliases；未来可加 `aliases:` 支持同义映射。

**Registry 的额外用途**：

- `memory_search` 工具可以暴露 `list_topics()` 和 `list_domains()` 子命令，让
  assistant 在对话中快速了解当前记忆覆盖了哪些领域。
- 用户可以手动编辑 `REGISTRY.md` 来合并同义词（例如把 `cron` 改成 `cron-scheduling`
  后，全局替换相关 memory 文件的 frontmatter）。
- 未来可以加 `aliases:` 字段支持同义映射，但第一版不做。

### 召回查询举例

```text
# 精确：Crabby 项目里的架构事实
memory_search(type=project, topic=crabby-架构, kind=fact)

# 广度：所有项目里关于定时任务的经验
memory_search(any_domain=[cron-scheduling])

# 时效：默认过滤掉 state=invalidated
memory_search(...)  # state=active 是默认
```

### Frontmatter 完整示例

```yaml
---
# ── Facet：分类维度（决定文件路径 + 主要检索轴）────────────
type: project                            # user / feedback / project / reference
topic: crabby-架构                        # 纵向边界：哪个项目/主题（必填，默认 general）
domain:                                  # 横向标签：哪类问题（数组，可空 = 不参与广度召回）
  - cron-scheduling
  - error-handling

# ── Facet：属性维度（记忆属性，用于过滤）──────────────────
kind: fact                               # fact / rule / pattern / mistake / goal / case / reflection
state: active                            # active / archived / invalidated

# ── Facet：事实有效期（不是文件维护时间）──────────────────
valid_from: 2026-05-19                   # 事实何时开始为真（null = 一直为真）
valid_to: null                           # 事实何时失效（null = 仍然有效）

# ── 链接元数据（记忆间关系，不属于 facet）────────────────
related:                                 # 相关记忆（轻量图谱）
  - crabby-cron-daemon-design
supersedes: []                           # 取代哪些旧记忆（旧的自动标 invalidated + valid_to）
derived_from: []                         # 来源（聚合时指向源记忆 name）

# ── 溯源元数据（从哪次对话产生，入队时快照，不属于 facet）──
session_id: s_abc123
conversation_id: c_xyz
branch_fingerprint: sha256...

# ── 维护元数据（文件身份与维护时间，不属于 facet）──────────
name: cron-retry-strategy                # kebab-case slug，全局唯一，= 文件名
created_at: 2026-05-19T14:30:00          # 文件第一次创建时间
updated_at: 2026-05-19T14:30:00          # 正文、facet 或链接关系最近实质更新时间
---

（Markdown body：记忆正文内容）
```

**文件路径**由分类维度派生：`<vault>/.crabby/memory/{type}/{topic}/{name}.md`

**检索时各维度的角色**：

| 场景 | 用哪些维度 |
|------|-----------|
| 精确召回（当前项目的事实） | `type=project, topic=X, kind=fact` |
| 广度召回（跨项目找同类经验） | `any_domain=[cron-scheduling]` |
| 时效过滤（只要当前有效的） | `valid_at=today`（valid_from ≤ 今天 且 valid_to 为空或 ≥ 今天） |
| 矛盾检查（写入前） | `type=<same>, topic=<same>, limit=10` |
| 聚合候选（maintenance） | `topic=X, kind=Y, state=active` |

## Frontmatter 规范

每个 memory 文件头部（详见上文 Facet 模型的完整示例）。以下是最小化示例（所有选填
字段取默认值时的样子）：

```yaml
---
name: user-role
type: user
topic: general
domain: []
kind: fact
state: active
valid_from: null
valid_to: null
related: []
supersedes: []
derived_from: []
session_id: s_abc123
conversation_id: c_xyz
branch_fingerprint: sha256...
created_at: 2026-05-19T14:30:00
updated_at: 2026-05-19T14:30:00
---
```

约束：

- `name` 是 kebab-case slug，全局唯一，与文件名一致。
- `type` 必须是 `user/feedback/project/reference` 之一。
- `topic` 必填。无明确归属时填 `general`。
- `domain` 数组可空。空意味着这条记忆不参与跨项目广度召回。
- `valid_from` / `valid_to` 默认 `null`。有明显时效性的记忆应写起止日期，便于未来过滤或自动失效。
- `session_id` / `conversation_id` / `branch_fingerprint` 是入队时的快照值，由
  `memory_write` 工具从 auto-save 上下文自动填入，不需要 agent 手动提供。

## 采集窗口与写入来源

auto-save 的采集窗口独立于最终沉淀边界。当前第一版规则：

1. 触发 auto-save 时，将 `session_id`、`conversation_id`、`branch_fingerprint` 和触发时
   的消息范围入队（这些值作为快照记录，写入 memory frontmatter 时直接使用）。
2. 后台处理时只使用入队时 snapshot，而不是处理时的当前 active conversation。
3. session manifest 的 `auto_save_checkpoints` 按 `conversation_id` 记录
   `last_reviewed_message_id`、`last_reviewed_revision`、
   `last_reviewed_branch_fingerprint` 和 `reviewed_at`。下一次触发时从该
   message 之后继续审阅。
4. 无 checkpoint 时只取当前窗口 `auto_save_interval * 2 + 4`，不回填老会话全量
   历史。新增消息超过窗口时按窗口大小分块，每块附带前 4 条消息作为只读背景。
5. fork conversation 时，如果父 conversation 的 checkpoint message 落在 fork 点及之前，
   新 conversation 会继承该 checkpoint；如果父 checkpoint 已经越过 fork 点，则不继承，
   避免跳过 fork 后未审阅内容。
6. 没有严格长期价值的批次也推进 checkpoint；语义是"已审阅"，不是"全部已记忆"。
   只有用户稳定偏好/事实、纠错反馈、项目决策、可复用材料、长期目标/约束会写入。
   但 LLM/daemon 异常、max-iteration exhaustion、或未被后续成功 `memory_write`
   收口的工具错误不会推进 checkpoint，避免把未写入的长期价值误标为已审阅。

## 专用记忆工具

新建专用工具，避免后台 agent 直接使用通用 `edit`。

`memory_write` 负责创建或更新单条记忆：

```text
memory_write(
  name: str,
  type: "user" | "feedback" | "project" | "reference",
  topic: str = "general",
  domain: list[str] = [],
  kind?: str,
  state: str = "active",
  valid_from?: str,           # ISO date 或 null
  valid_to?: str,             # ISO date 或 null
  body: str,
  related: list[str] = [],
  supersedes: list[str] = [],
  derived_from: list[str] = [],
) -> {path, name, created: bool, updated: bool, registry_changes: list[str]}
```

写入规则：

- 只能写 `<vault>/.crabby/memory/`。
- 一条记忆一个 Markdown 文件，路径由 `type/topic/name.md` 派生。
- 写入前必须读取/更新 registry，优先复用已有 topic/domain。
- 写入 registry 和 memory 文件要尽量保持原子性；失败时返回明确错误，不静默丢失。
- **写入前矛盾检查**（见下文"矛盾检测与冲突处理"）。

### 矛盾检测与冲突处理

新记忆可能与已有记忆冲突（例如"用 SQLite 做 session 存储" vs "改用 PostgreSQL"）。
设计目标：让 agent 在写入前感知潜在冲突，由 LLM 判断处理方式，但不做全量语义比对。

**低成本检查策略**：

`memory_write` 内部在实际写入前，自动执行一次窄范围查询：

```text
memory_search(type=<same>, topic=<same>, limit=10)
```

只返回 `name + type + topic + domain + kind + updated_at`，不返回 body，避免额外摘要字段。
候选集很小，LLM 可按名称和元数据先判断是否需要进一步 `read`。

查询结果作为 `memory_write` 返回值的一部分（`potential_conflicts` 字段）返回给 agent：

```text
) -> {
  path, name, created: bool, updated: bool,
  registry_changes: list[str],
  potential_conflicts: list[{name, type, topic, domain, kind, updated_at}]  # 同 topic+type 下已有记忆
}
```

**agent 处理流程**：

1. 如果 `potential_conflicts` 为空，直接写入。
2. 如果有候选冲突，agent 判断：
   - **更新已有**：调 `memory_write(name=<existing>)` 覆盖更新（修改 body + updated_at）。
   - **取代旧的**：创建新记忆，`supersedes: [old-name]`；旧记忆自动标记
     `state: invalidated`，`valid_to: <today>`。
   - **并存**：判断不矛盾，只是补充，正常写入。

**为什么不做语义比对**：

- 全量向量搜索需要 MemPalace 在线，违背保底原则。
- 同 `topic + type` 的窄范围查询已经把候选集缩到 <10 条，LLM 可先看元数据，必要时再读正文。
- 真正的语义矛盾检测可以作为 MemPalace 在线时的增强：写入后调 `mempalace_search`
  做跨 topic 的语义查重，发现问题再补标 `related` 或 `supersedes`。

`memory_search` 负责结构化召回。它消费 facet 字段做过滤：

```text
memory_search(
  # 模式选择
  mode: str = "search",      # "search" | "list_topics" | "list_domains" | "list_registry"

  # facet 过滤（mode=search 时使用）
  type?: str,                # user/feedback/project/reference
  topic?: str,               # 精确匹配
  domain?: list[str],        # 必须包含全部（AND）
  any_domain?: list[str],    # 包含任一（OR），用于广度召回
  kind?: str,
  state?: str = "active",    # 默认只看 active
  valid_at?: str,            # ISO date；过滤 valid_from <= date 且 (valid_to is null 或 >= date)

  # 辅助
  name_prefix?: str,
  limit?: int = 20,
) -> list[{path, name, type, topic, domain, kind, updated_at}]
   | {topics: list[str], domains: list[str]}  # list 模式返回 registry 内容
```

**mode 说明**：

- `search`：按 facet 过滤返回记忆元数据列表。
- `list_topics`：返回 REGISTRY.md 中所有已有 topic。
- `list_domains`：返回 REGISTRY.md 中所有已有 domain。
- `list_registry`：返回完整 registry（topics + domains）。

**写入前必须查看 registry**——这是写入协议的一部分，确保 agent 看到已有词表再决定
复用还是新建。实现上可以让 `memory_write` 内部强制执行，不依赖 LLM 自觉。

典型查询模式：

```text
# 精确：当前项目的架构事实
memory_search(type=project, topic=crabby-架构, kind=fact)

# 广度：跨项目找同类经验
memory_search(any_domain=[cron-scheduling])

# 错题本：用户犯过的错
memory_search(type=user, kind=mistake)
```

MemPalace 在线时，`memory_search` 作为"精确召回"通道与 `mempalace_search` 的"语义召回"
互补；MemPalace 不在线时，它是唯一的结构化召回手段。

## Diary 设计

### 存放位置

设置项：`diaryPath`，默认值建议 `Journal/`，由用户在 Obsidian 插件设置页配置。
Crabby 不强制目录结构，但内置 diary skill 的默认模板和写入规则建议按
`<diaryPath>/<YYYY>/<MM>/<YYYY-MM-DD>.md` 组织。

### 内置 Diary Skill 与模板化

Diary 由内置 `diary` skill 负责规范写入和修改行为。skill 携带默认模板、章节约定、
追加规则、语气约束和"不要覆盖用户原文"等边界。模板由用户在设置页配置，类似
Obsidian Templates 插件的语义。模板支持变量：

| 变量 | 含义 |
| --- | --- |
| `{{date}}` | `YYYY-MM-DD` |
| `{{time}}` | `HH:mm` |
| `{{session_id}}` | 触发本次写入的 session |
| `{{summary}}` | 本次 auto-save agent 生成的摘要 |
| `{{topics}}` | 本次涉及的 topic 列表 |
| `{{domains}}` | 本次涉及的 domain 列表 |

默认模板（用户可改）：

```markdown
---
date: {{date}}
---

# {{date}} 日记

## 今日要点

{{summary}}

## 涉及主题

{{topics}}


## 关联记忆

(由 agent 在写入时填入相关 memory 文件链接)
```

### 写入策略

- **一天一文件**：当天首次 auto-save 创建文件；同一天后续 auto-save **追加 H2 段落**，
  不覆盖。
- **追加段头**带时间戳和 session 链接，便于翻阅时知道每段来源。
- Diary 不放进 `MEMORY.md` 索引——它是时间线日志，不是按主题召回的对象。需要时用
  Obsidian 的 Daily Notes 或日期搜索找。
- Diary skill 可以引用本次写入产生的 memory 文件链接，但不把 Diary 当作 memory
  source of truth。

### Diary 与 memory/ 的关系

- Diary 是**人读的时间线**，记录"今天发生了什么"。
- `memory/project/<topic>/<name>.md` 是**模型用的事实库**，记录"这个主题的关键事实"。
- 两者可以互相引用：Diary 里链到当天产生的 memory 文件；memory 文件可以反向链到
  首次出现的 Diary 段落。

## 与 MemPalace 的关系

落地后，MemPalace 的角色调整为：

- **不再是 source of truth**。
- **作为派生向量索引**：auto_save 写完 Vault Markdown 后，调 `mempalace_add_drawer`
  把同一份内容索引进去。
- **作为可选语义召回通道**：`memory_search` 拿不到结果或用户提问偏向语义时，再调
  `mempalace_search`。
- **作为探索性关联发现**：`mempalace_find_tunnels` 提供跨 Wing 的后验关联发现，与
  domain 的先验分类召回互补。domain 回答"我主动标注了这条经验属于哪类问题"，
  tunnel 回答"系统发现这两个项目之间碰巧有什么共同点"。tunnel 在新项目刚开始、
  尚无足够 domain 标注时尤其有用。
- **可独立重建**：MemPalace 数据丢失时，从 Vault 重新喂一遍即可恢复。

如果未来 MemPalace 不再使用，沉淀链不受影响——Vault 本身完整。

## 未决问题

1. **topic 命名权归 LLM 还是用户？**
   倾向：LLM 决定，但写入前先读 registry，让 LLM 选择已有 topic 或新建；用户可手改
   文件名和 frontmatter，之后通过校验/重建工具同步 registry 与机器索引。
   **实现状态**：`memory_write` 已强制 ensure_terms，写入前自动读 registry 并追加新词。
   用户手改后的 registry 重建工具尚未实现。
2. **domain 是预定义词表还是自由打？**
   倾向：自由打 + 写入时先 list 已有 domain 让 LLM 选已有或新建（与 topic 一致策略）。
   预定义词表会卡死成长，但不约束又会漂移；折中是 LLM "看过再写"。
   **实现状态**：已实现。`memory_search(mode="list_registry")` 暴露已有词表，
   `memory_write` 自动追加新 domain 到 registry。
3. **kind 词表够用吗？**
   当前词表收敛为：`fact / rule / pattern / mistake / goal / case / reflection`。
   不单设 `decision`，落定的决策作为 `fact` 保存，理由和取舍写在正文；`case` 替代
   `anecdote`，避免变成口语化杂物筐。`reflection` 服务于复盘、成长记录和聚合产物。
   是否还需要其他 kind？待实际使用中验证，但第一版优先保持克制。
   **实现状态**：已实现。`facets.py` 中 `VALID_KINDS` 定义了这 7 个值并做校验。
4. **`feedback/` 是否需要专门的"why / how to apply"结构化字段？**
   Claude Code 的 feedback memory 会要求 agent 写明 `**Why:**` 和 `**How to apply:**`。
   值得照抄，因为没有 why 的反馈在边缘场景没法判断是否适用。
   **实现状态**：未实现为结构化字段。当前 body 是自由 Markdown，依赖 LLM 在正文中
   自行组织 Why/How to apply 段落。
5. **第一版要不要做链接（supersedes / related）？**
   做：记忆图谱基础就有了，将来 MemPalace 的 KG 写入有上游。
   不做：先靠 facet，链接以后补（更稳）。
   **实现状态**：已实现写入侧。`memory_write` 支持 related/supersedes/derived_from
   字段，supersedes 会自动标记旧记忆 invalidated。但 `memory_search` 尚不支持按
   链接关系查询。
6. **Diary 模板存放位置？**
   候选：(a) 内置 diary skill 自带默认模板；(b) Vault 内
   `<vault>/.crabby/templates/diary.md` 覆盖默认；(c) 插件设置项里直接存字符串；
   (d) Obsidian Templates 插件目录复用。倾向 (a)+(b)：skill 管行为，Vault 文件管
   用户可编辑模板。
   **实现状态**：模板文件已落地在 `<vault>/.crabby/templates/diary.md`（layout.py
   和 backendRuntime.ts 均会种子创建）。Diary skill 本身未实现。
7. **MEMORY.md 是否需要机器生成热入口？**
   当前定位是读取规则和热入口，不是全量索引。未决点是 Hot Entries 由用户维护，还是
   由 memory_search 根据近期访问/更新时间生成一小段可注入摘要。
   **实现状态**：MEMORY.md 种子文件已创建，内容为静态规则文本。动态热入口生成未实现。
8. **记忆聚合何时做？**
   第一版不做自动聚合。设计草案已写入上文"未来：记忆聚合设计草案"章节，待第一版

11. **topic 中文命名 vs kebab-case 约束？**（新增）
   当前 `facets.py` 的 `_check_topic` 校验器要求 topic 为 `^[a-z0-9][a-z0-9\-]*$`

   `健身计划`、`typescript-学习`）。需要决定：放宽校验支持中文/Unicode，还是统一
   要求英文 kebab-case 并更新文档示例。

## 未来：记忆聚合设计草案

第一版不做自动聚合，但此处记录设计方向，供后续实施参考。

### 问题

随着使用时间增长，同一 topic 下会积累大量细粒度记忆（例如 10 条关于 cron 失败处理的
独立经验）。碎片化导致：
- 召回结果过多，agent 需要逐条 read 才能综合。
- 重复信息占用搜索结果 limit 配额。
- 没有"全局结论"层级的知识表示。

### 聚合机制

**触发条件**：maintenance cron 定期扫描（建议每周一次），发现同 topic + 同 kind 下
超过 N 条（建议 N=5）active 记忆时触发聚合候选。

**执行者**：独立的 maintenance agent（不是 auto-save agent），使用 `memory_write` +
`memory_search` 工具。

**聚合流程**：

1. `memory_search(topic=X, kind=Y, state=active)` 获取候选列表。
2. 逐条 `read` 候选记忆的 body。
3. LLM 综合生成一条 `kind: reflection` 的新记忆，提炼共性结论。
4. 新记忆的 `derived_from` 指向所有源记忆的 name。
5. 源记忆标记 `state: archived`（不删除，保留溯源）。
6. 如果源记忆有不同的 domain，新记忆取并集。

**聚合产物示例**：

```yaml
---
name: cron-reliability-patterns
type: project
topic: crabby-架构
domain:
  - cron-scheduling
  - error-handling
kind: reflection
state: active
derived_from:
  - cron-retry-strategy
  - cron-idempotency-requirement
  - cron-timeout-handling
  - cron-overlap-prevention
  - cron-failure-alerting
---

所有定时任务应满足三个可靠性保证：
1. 幂等性：重复执行不产生副作用
2. 指数退避：失败重试间隔递增，上限 1 小时
3. 互斥锁：同一任务不允许并发执行
```

**不聚合的情况**：

- `type=user` 的记忆通常是独立事实，不适合合并。
- `kind=mistake` 保留原始上下文更有价值，不建议聚合。
- 跨 topic 的记忆不聚合（那是 domain 横向召回的职责）。

### 与 MemPalace 的关系

聚合完成后，新的 reflection 记忆正常双写到 MemPalace。被 archived 的源记忆可以选择
从 MemPalace 中删除（减少向量库噪音），也可以保留（保持语义搜索的覆盖面）。第一版
建议保留，后续根据检索质量数据决定。
