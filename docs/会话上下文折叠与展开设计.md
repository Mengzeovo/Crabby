# 会话上下文折叠与展开设计

最后更新：2026-05-24
状态：未来设计草案，记录“会话上下文折叠/展开”的长期方向。

## 文档定位

本文记录一个未来的上下文管理思路：把一次会话里大量的工具调用、并行执行、临时推演和中间结果，折叠成一个更短的可复用摘要；当后续问题真的需要细节时，再按引用展开回原始轨迹。

它介于 [会话设计.md](会话设计.md) 和 [记忆沉淀设计.md](记忆沉淀设计.md) 之间：

- 会话设计负责“历史怎么存、分支怎么拼”。
- 记忆沉淀设计负责“哪些内容值得长期保留”。
- 折叠与展开负责“同一段会话历史怎么以不同粒度被消费”。

## 核心想法

一次用户请求通常不是单条消息，而是一段操作过程：模型可能要调用多个工具，可能要并行查资料，可能要修改文件并验证结果。对当前回合来说，这些细节很重要；但对后续普通对话来说，往往只需要知道：

1. 用户要什么。
2. 做了什么。
3. 得到了什么结果。
4. 产生了哪些副作用。

所以这里的“折叠”不是删除原始过程，而是把它收敛成一个更小的上下文胶囊。

## 术语

- **原始轨迹**：完整的用户消息、模型推理、工具调用、工具结果和错误。
- **折叠块**：对一段原始轨迹生成的摘要视图。
- **展开**：按引用取回折叠块背后的原始轨迹或更细粒度子块。
- **上下文胶囊**：可以直接放进后续 LLM context 的折叠结果。

## 设计原则

- **不丢原文**：折叠是派生层，不是存档替换。
- **可追溯**：每个折叠块都能回到对应的 message、tool result、file change 或 branch。
- **低噪音**：后续上下文默认只注入折叠结果，不重复塞入整段工具链。
- **可展开**：一旦用户追问细节，或模型判断需要证据，就能回看原始过程。
- **和分支一致**：折叠块必须绑定 session / conversation / branch fingerprint，不能跨分支乱复用。

## 折叠单元

比较自然的折叠单位有三种：

1. **一次用户请求**：从用户提问到最终回复，整段折成一个块。
2. **一次工具密集回合**：模型多轮调用工具、最后产出结论，折成一个块。
3. **一个并行工作段**：多个工具并发完成，折成一个带子任务结果的块。

对折叠块来说，最少要保留这些字段：

- 用户意图
- 关键输入
- 执行动作
- 关键输出
- 副作用
- 警告和失败
- 原始引用
- 索引键（`index_keys`）：用于隐式展开时检索，至少包含涉及的文件路径、工具名、关键实体、意图标签

“只记输入/输出”通常不够，因为后续最常追问的是“改了什么”“为什么这么做”“哪里失败过”。

### 折叠触发策略

折叠单元只说明“折成多大一块”，还需要一个独立的“何时折”策略。三种候选：

1. **每回合即折**：每次用户请求结束就生成折叠块，实现简单，但折叠质量受限于单回合信息量。
2. **阈值触发**：上下文逼近 token 阈值时再折，能折出信息密度更高的块，但折叠时机不可预测，且单次折叠成本高。
3. **模型主动请求**：模型在判断“这段后续不会用到”时主动请求折叠，灵活但依赖模型自觉性。

短期建议采用 **每回合即折** 作为默认策略，其它两种作为可选增强，避免一开始就把触发逻辑做复杂。

## 展开方式

展开可以有两种触发：

- **显式展开**：用户明确说“展开刚才那段”。
- **隐式展开**：当前问题依赖折叠块里的细节，系统自动把相关原始轨迹取回。

展开不一定要一次性放回全部原文。更好的做法是按需展开到合适粒度：

- 先给摘要。
- 需要工具结果时展开工具段。
- 需要文件变化时展开对应 file change。
- 需要错误排查时展开失败链路。

隐式展开是这套设计里最难的一环：让模型判断“当前问题是否依赖被折叠的细节”，本质是个检索问题。它依赖折叠块上的 `index_keys`（见“折叠单元”）作为命中维度——没有显式索引，隐式展开就会退化成“要么全展开、要么不展开”。实现上可以走两步：先用 `index_keys` 做粗筛，再让模型在候选块上判断是否真的需要展开。

## 与现有系统的关系

这个思路和现有的 session / branch 设计是兼容的：

- `session_id` 和 `conversation_id` 仍然是主索引。
- `branch_fingerprint` 可以作为折叠块失效或重建的判定依据。
- `revision` 变化后，相关折叠块也应重新生成或标记失效。

`revision` 的失效策略需要单独想清楚，不能一句“变了就重建”带过：长会话里改动频繁，全量重建很贵；但如果不重建，折叠摘要里引用的文件状态会和当前 `revision` 不一致，模型读了会基于过期信息做决策。可行的折中是：

- 折叠块绑定生成时的 `revision`，并保留对涉及文件的引用。
- 当某个文件 `revision` 变化时，把相关折叠块标记为 `stale` 而不是立即重建。
- `stale` 块仍然可读（带提示），只有在隐式/显式展开时才按需 lazy 重建。

这样可以避开“写放大”，又不会让模型读到无标注的过期摘要。

它也和长期记忆不同：

- **折叠**处理的是“本次会话里怎么少占上下文”。
- **记忆**处理的是“哪些结论值得长期留存”。

二者可以衔接，但不该混成一个概念。某个折叠块里如果抽出了稳定事实，那是记忆候选；折叠本身只是会话压缩。

## 一个简单判断

如果一段内容满足下面任一条件，就值得优先折叠：

- 工具调用很多。
- 中间步骤很多，但最终只需要一个结论。
- 内容未来大概率只会被引用，不会被全文阅读。
- 细节可追溯，但不适合每次都塞进上下文。

## 后续可演进方向

- 在聊天 transcript 里显示可折叠块。
- 为折叠块增加稳定 `span_id`。
- 为展开提供后端级引用接口。
- 让模型在必要时主动请求展开。
- 让折叠摘要与长期记忆抽取共享部分中间结构。

这条线如果继续往前走，Crabby 会更像一个“可压缩、可回放、可展开的工作记忆系统”，而不只是聊天记录系统。

## 未决问题

下面这些点目前没有明确答案，需要在真正落地前再想一轮：

- **折叠成本 vs. 节省收益**：折叠本身要跑一次 LLM，如果每回合都折，短会话里折叠成本可能比省下来的上下文还贵。需要一个简单的启发式（比如回合内 token 数 / 工具调用数超过阈值才折）来避免无效折叠。
- **摘要忠实度**：折叠摘要由 LLM 生成，存在事实漂移风险——尤其是“执行动作”和“副作用”字段。是否需要对关键字段（如文件改动列表、命令执行结果）走结构化抽取而不是自由文本，避免模型在摘要里编造？
- **展开的上下文预算**：隐式展开如果命中多个折叠块，可能一次性把上下文撑爆，反而违背折叠的初衷。需要一个展开预算和优先级排序策略。
- **跨会话引用**：当前设计假设折叠块绑定 `session_id`，但用户经常会在新会话里追问旧会话的细节。是否允许跨会话展开？如果允许，权限和分支一致性怎么保证？
- **与 compaction 的边界**：宿主（Claude Code、其它 IDE 集成）已经有自己的上下文压缩机制。本设计的折叠层应该替换它、并存、还是只在宿主不压缩时启用？这关系到这套机制最终是不是真的能落到 Crabby 自己的运行时里。
