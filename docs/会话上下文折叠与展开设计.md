# 会话上下文折叠与展开设计

最后更新：2026-05-22
状态：未来设计草案，记录“会话上下文折叠/展开”的长期方向。

## 文档定位

本文记录一个未来的上下文管理思路：把一次会话里大量的工具调用、并行执行、临时推演和中间结果，折叠成一个更短的可复用摘要；当后续问题真的需要细节时，再按引用展开回原始轨迹。

它介于 [会话设计.md](会话设计.md) 和 [记忆沉淀设计.md](记忆沉淀设计.md) 之间：

- 会话设计负责“历史怎么存、分支怎么拼”。
- 记忆沉淀设计负责“哪些内容值得长期保留”。
- 折叠与展开负责“同一段会话历史怎么以不同粒度被消费”。

## 核心想法

一次用户请求通常不是单条消息，而是一段操作过程：模型可能要调用多个工具，可能要并行查资料，可能要修改文件并验证结果。对当前回合来说，这些细节很重要；但对后续普通对话来说，往往只需要知道：

1. 用户要什么。
2. 做了什么。
3. 得到了什么结果。
4. 产生了哪些副作用。

所以这里的“折叠”不是删除原始过程，而是把它收敛成一个更小的上下文胶囊。

## 术语

- **原始轨迹**：完整的用户消息、模型推理、工具调用、工具结果和错误。
- **折叠块**：对一段原始轨迹生成的摘要视图。
- **展开**：按引用取回折叠块背后的原始轨迹或更细粒度子块。
- **上下文胶囊**：可以直接放进后续 LLM context 的折叠结果。

## 设计原则

- **不丢原文**：折叠是派生层，不是存档替换。
- **可追溯**：每个折叠块都能回到对应的 message、tool result、file change 或 branch。
- **低噪音**：后续上下文默认只注入折叠结果，不重复塞入整段工具链。
- **可展开**：一旦用户追问细节，或模型判断需要证据，就能回看原始过程。
- **和分支一致**：折叠块必须绑定 session / conversation / branch fingerprint，不能跨分支乱复用。

## 折叠单元

比较自然的折叠单位有三种：

1. **一次用户请求**：从用户提问到最终回复，整段折成一个块。
2. **一次工具密集回合**：模型多轮调用工具、最后产出结论，折成一个块。
3. **一个并行工作段**：多个工具并发完成，折成一个带子任务结果的块。

对折叠块来说，最少要保留这些字段：

- 用户意图
- 关键输入
- 执行动作
- 关键输出
- 副作用
- 警告和失败
- 原始引用

“只记输入/输出”通常不够，因为后续最常追问的是“改了什么”“为什么这么做”“哪里失败过”。

## 展开方式

展开可以有两种触发：

- **显式展开**：用户明确说“展开刚才那段”。
- **隐式展开**：当前问题依赖折叠块里的细节，系统自动把相关原始轨迹取回。

展开不一定要一次性放回全部原文。更好的做法是按需展开到合适粒度：

- 先给摘要。
- 需要工具结果时展开工具段。
- 需要文件变化时展开对应 file change。
- 需要错误排查时展开失败链路。

## 与现有系统的关系

这个思路和现有的 session / branch 设计是兼容的：

- `session_id` 和 `conversation_id` 仍然是主索引。
- `branch_fingerprint` 可以作为折叠块失效或重建的判定依据。
- `revision` 变化后，相关折叠块也应重新生成或标记失效。

它也和长期记忆不同：

- **折叠**处理的是“本次会话里怎么少占上下文”。
- **记忆**处理的是“哪些结论值得长期留存”。

二者可以衔接，但不该混成一个概念。某个折叠块里如果抽出了稳定事实，那是记忆候选；折叠本身只是会话压缩。

## 一个简单判断

如果一段内容满足下面任一条件，就值得优先折叠：

- 工具调用很多。
- 中间步骤很多，但最终只需要一个结论。
- 内容未来大概率只会被引用，不会被全文阅读。
- 细节可追溯，但不适合每次都塞进上下文。

## 后续可演进方向

- 在聊天 transcript 里显示可折叠块。
- 为折叠块增加稳定 `span_id`。
- 为展开提供后端级引用接口。
- 让模型在必要时主动请求展开。
- 让折叠摘要与长期记忆抽取共享部分中间结构。

这条线如果继续往前走，Crabby 会更像一个“可压缩、可回放、可展开的工作记忆系统”，而不只是聊天记录系统。
